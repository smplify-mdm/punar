Sect I · Card anatomy register

Every toast is the same drawing: meta row, rule, one sentence, actions. Nothing gets a second sentence.

01Meta row

Tracked mono, middle-dot separators: kind, source, project — APPROVAL · CLAUDE CODE · ATLAS — with the live datum right-aligned (an expiry, a timestamp). The masthead grammar, shrunk to a card.

02One sentence

The claim is a single plain sentence in Instrument Sans 500. If it needs two, it isn't a toast — it opens a surface. The §73 anatomy (what, who, which policy, next step) fits in the card or the card links out. spec §73

03Actions

Approve is the surface's one filled ok-green button — the action-color rule from the greeter. Dismiss is ghost and never destroys: it files the card to the center. Kbd hints are printed on the buttons, not hidden in docs. spec §12.1 · §28

04Calm variant

SCREENSHOT · SAVED carries no color and a hairline rule instead of ink — a screen with no status to report contains no color. Same anatomy, quieter voice.

Sect II · Center and DND register

The center is a ledger of interruptions, grouped by who spoke — and quiet has one exception, stated on the surface.

01Grouped by source

Sources are tracked-mono group heads: CLAUDE CODE · ATLAS, SYSTEM, PUNAR-AGENTD. A notification always names its speaker; anonymous interruptions do not exist.

02Unknown-AI alert

The foo-agent row is the only red in the panel: SUSPECTED, NOT CERTAIN, with INSPECT linking to the §25 view in Plate D-005. Detection wears a dashed SIMULATED tag until M10 ships it. spec §25 · §1.22

03DND policy

Do-not-disturb silences toasts, never the record — and it never silences approval-expiry warnings. A pending approval is a deadline someone is waiting on; deadlines outrank quiet. The rule is printed beside the toggle, in amber, because it is a promise about the warn state. spec §28 · §73

04Approvals resolve

X and CLEAR ALL skip the approval row. Approvals are decisions, not noise — they leave the center by being approved, denied, or expiring, and every exit lands in the audit trail as evt_50x.

Sect III · OSD-as-instrument register

Volume is a reading on a dial, not a fluid in a tube — twenty discrete ticks, five percent each.

01Segmented bar

The tick bar quantizes to real steps, like the boot dial's rim: lit ticks are panel-fg, unlit are panel-edge, no gradient and no partial tick. What you see is exactly the value the capability layer holds.

02Mono percentage

The number is Geist Mono, tabular-nums, right-aligned so it never jitters while held keys repeat. At zero the label reads MUTED in panel-ink-3 — a state word, not a color, because silence is not an error.

03Panel surface

OSD overlays live on the panel system per the surface assignment — they float over anything, including full-screen video, and the near-black card holds contrast everywhere. No status color appears: level is a reading, not a judgment.

04Honest backlight

In VM builds there is no physical backlight; the brightness row carries a dashed SIM · VM tag rather than pretending. Solid claims require an operating path. spec §1.22

Sect IV · Keyboard register

Notifications, screenshots, and clipboard are on the §12.1 list: every action here has a key, and every key is printed.

01Toast keys

A approves, D files to center — no pointer travel to the corner of the screen while an agent waits. The bindings render on the buttons themselves. spec §12.1

02Center keys

J/K walk the list, X dismisses, ↵ opens the source surface, C clears, D toggles quiet. The footer names all of them — discoverability is a printed fact, not a memory test. spec §12.3

03Unmanaged-first

The demo defaults to a personal device: the approval cites POLICY · PERSONAL DEFAULTS — the user's own gates, protecting the user first. Enrolling only annotates: the org name joins the masthead and a MANAGED pill joins the card; nothing moves. spec §3.2 · §20

Sect V · Implementation notes

Design mockup — the daemon and shell pieces land across Milestones 1–10; this page is the acceptance reference.

01Shell

Quickshell layer-shell surfaces consuming shell/theme/punar-tokens.json: toast stack and OSD in M1 (audio/brightness via the typed capability layer), notification center with M1's shell frame. Toasts speak the freedesktop notification protocol so third-party apps inherit the anatomy.

02Approval path

The approval toast is Plate D-003's overlay in miniature: same apr_123 object from punard (M9), same expiry clock, same audit event on resolution. One approval, three renderings — toast, overlay, CLI — one source of truth. spec §28 · §10

03Detection alert

The unknown-AI row arrives with M10 shadow-AI detection; until then the fixture (foo-agent, api.foo.ai) renders behind the dashed simulated tag. DND state and the expiry-breakthrough rule live in punard so punarctl reports them identically.
