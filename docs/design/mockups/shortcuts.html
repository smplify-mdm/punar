A shortcut you cannot find is a shortcut you do not have.

Spec §12.3 asks for two things — hold PUNAR and see the chords, press ? and read them all — and then states the requirement plainly: do not make people memorise dozens of undocumented shortcuts. Punar ships sixty-four described binds today and no surface that names a single one of them; a user sitting in front of a window they wanted closed had to ask another human what PUNAR+Q was. That is exactly the failure §12.3 names. The fix is not a documentation page. It is two surfaces generated from the compositor's own binding table, so the reference cannot drift from the machine it describes.

Sect I · Anti-drift register

The overlay is generated from the compositor's binding table on every session, and there is no second list anywhere — because a second list is a surface that lies the moment a chord changes.

01The rule

The shell renders hyprctl binds -j and nothing else. Not a QML array, not a Markdown table, not a generated header — the live table the compositor is currently dispatching from. A hardcoded list is a second source of truth, and a second source of truth is a promise to be wrong later: the day someone moves the assistant scratchpad to PUNAR+SHIFT+A (M7 did exactly that), a hand list keeps confidently printing the old chord to a user who then presses it and gets nothing. Punar's whole posture is that a surface does not claim what is not true. spec §1.22 · §12.3 · design language §7

02The transform

Four fields per bind, four rules. modmask + key → the chord: the mask is decoded against the standard modifier bits (SHIFT 1, CTRL 4, PUNAR 64 — so PUNAR is 64, PUNAR+SHIFT 65, PUNAR+CTRL 68) and rendered in one canonical order — PUNAR, CTRL, SHIFT, ALT — never in bitmask order, so two chords with the same modifiers always read identically. description → the label, verbatim, never rewritten or title-cased by the shell. dispatcher → the section (Sect III). submap → the mode block: a non-empty submap field means the row belongs to a mode, not to the global grammar. The keysym gets a twelve-entry display table (bracketleft → [, Return → ↵, escape → ESC, arrows to glyphs); an unrecognised keysym renders uppercased verbatim and is never dropped. spec §12.3

03No description · no row

A bind whose description is empty is excluded. Not shown with its dispatcher as a fallback label, not shown as "unnamed" — excluded. That absence is the enforcement: an undescribed binding is invisible to every user of the machine, so the pressure to write a label lands on the person adding the binding, at the moment they add it, instead of on some later documentation pass that never happens. punar-binds.conf already uses bindd for all sixty-four binds precisely so this rule costs nothing today; the counter in the help footer prints 0 undescribed, and the number rising is the alarm. spec §1.22 · §11.8

04Order · config order

Rows inside a section appear in the order the compositor returns them, which is the order they are written in punar-binds.conf — focus, move, groups, resize, modes, layouts, workspaces, overview, apps, scratchpads, displays, screenshots, session. Not alphabetical: alphabetical order puts "Close window" above "Focus left" and destroys the grammar the config already teaches. There is no sort function in the shell to get wrong, and the maintainer reorders the reference by reordering the config — one place. The cost is real and stated: file order becomes a design surface. To verify — that hyprctl binds -j preserves registration order on 0.56.2. If it does not, the shell sorts by a stable dispatcher-order list instead, and the register is amended, not the claim. design language §7

05The range fold

Nine workspace binds are one idea. Rows fold when — and only when — the dispatcher is identical, the modmask is identical, the keys form a contiguous digit run, and the descriptions differ solely by that trailing integer: Workspace 1…9, Move window to workspace 1…9. Mechanical, reversible, and it hides nothing: sixty-four binds become forty-eight rows, and both numbers are printed in the help footer so the fold is auditable at a glance. Directional families (Focus left/down/up/right) do not fold — their labels differ by a word, not an index, and four verbs are four things to learn. design language §7

Sect II · Two-surface register

One source, two commitments: the held overlay is a glance you cannot touch, the help surface is a document you can work in.

01Hold · what it shows

It shows exactly the bindings the modifier you are holding can reach right now — every bind whose modmask is PUNAR alone, twenty-two rows in three columns. That is a mechanical filter, not a curated summary: nobody chooses which chords are "the ones people forget", the held modifier does. Adding SHIFT while still holding swaps the overlay to the fifteen PUNAR+SHIFT rows; adding CTRL swaps to the four PUNAR+CTRL rows. The footer counts the layers you are not looking at, so the overlay never implies it is the whole grammar. spec §12.3

02400 ms

The hold delay is 400 ms. At 0 ms the overlay flashes on every chord you already know — PUNAR+Q would strobe a panel across the screen — which prices fluency in visual noise and teaches people to dread their own leader key. At 1000 ms the question has already been abandoned; a second of nothing reads as "this does not do anything" and the user goes to a browser. A confident chord completes well under 250 ms, and hesitation is legible above roughly 350; 400 ms sits in the gap, above the fast typist and inside the pause that means "I have forgotten this". The timer exists only between press and either the chord or the deadline — nothing runs at rest. spec §12.3 · §6.3

03Hold · commitment

Transient, non-interactive, and unfocusable: a layer-shell surface with keyboardFocus: none and an empty input region, so it is literally click-through and cannot steal a keystroke from the window under it. Bottom-centred, 82% of the display width, 24 px above the bottom edge — below the bar (which owns modality and must stay readable) and clear of the top two thirds where the focused window's own header and first lines live. It appears with a 150 ms opacity fade and disappears on the release frame with no fade-out: modifier state is binary, and a ghost that outlives the key is a surface lying about the keyboard. design language §4 · §6 · spec §13.4

04Help · commitment

Persistent, focusable, complete: all forty-eight rows, every layer, every mode, on paper. Opened with PUNAR + / (and with ? from inside any shell surface that already owns the keyboard — a bare question mark cannot be a global bind without eating the character out of every text field). / focuses the filter, ↑↓ walk the visible rows, ESC closes and returns focus to the window that had it. Panel for the glance, paper for the document — the transient surface is an OSD and the persistent one is a shell surface, which is the surface assignment the design language already makes. design language §6 · spec §12.1

05Help does not execute

↵ on a selected row does nothing. The help surface teaches a chord; it never runs one. Running it would mean the shell dispatching the row's dispatcher itself — a second execution path alongside the compositor's own, testable only by having both — and it would teach the wrong lesson, because the key the user pressed was not the chord they came to learn. The surface that runs things by name already exists and is one chord away: the command center, PUNAR+Space (§12.2). Reference and execution are deliberately different rooms. spec §12.2 · §12.3

06Overflow · 1366 × 768

Different answers, because the surfaces have different escape routes. Help: three columns above 1200 logical px, two above 900, one below; sections stay whole and a section longer than a column continues under a repeated header; the body is one vertical scroll (never a nested one), keyboard selection scrolls itself into view, and filtering is the real overflow answer — two letters usually beat any amount of scrolling. Hold: it may not scroll, because you cannot scroll a surface that vanishes when you let go. It drops to two columns, then shrinks the label to 12 px, and if a layer still does not fit, the final row is replaced by an honest count — +6 more · ? for all — because a reference that silently truncates is worse than one that admits it. Today's twenty-two-row PUNAR layer fits three columns at 1366 with room. spec §5.1 · §12.3

Sect III · Grouping and mode register

Sections come from the dispatcher, never from the label — and when the section table misses, the row still appears with its true chord under OTHER, because grouping may degrade but a row may not.

01Five sections

In the order a person reaches for them: WINDOWS (focus, move, close, resize) · WORKSPACES AND PROJECTS (1…9, move-to, overview) · LAYOUTS (groups, fullscreen, float, pin, centre, presets) · SURFACES (command center, AI panel, terminal, browser, scratchpads — and System Control and approvals when they take chords) · SESSION (screenshots, end session). Frequency, roughly, and consequence: the section that ends things is last. Section order is fixed in the shell; row order inside a section is the config's (Sect I·04). spec §12.3 · §13 · §14

02Dispatcher → section

A closed table keyed on the dispatcher — a vocabulary of about fifteen Hyprland verbs, not forty bindings: movefocus · movewindow · killactive · submap · resizeactive → WINDOWS; workspace · movetoworkspace → WORKSPACES; togglegroup · moveintogroup · moveoutofgroup · changegroupactive · fullscreen · togglefloating · pin · centerwindow → LAYOUTS; togglespecialworkspace → SURFACES; exit → SESSION. A new binding on a verb the table already knows files itself with no code change at all — which is the point: the table is small, closed, and changes an order of magnitude less often than the binds do. spec §13.2 · §13.6

03exec · and OTHER

exec is not a verb, so it is disambiguated by the command, which Punar owns: a command containing ipc call <target> takes the section of that shell target (overview → workspaces, commandcenter and aipanel → surfaces) — a contract the shell itself defines and therefore cannot drift from — and a five-entry command table covers the rest (punar-layout.sh → layouts, terminal and browser → surfaces, grim → session). Rename one of those and its row does not vanish and is not mislabelled: it falls to OTHER, visible, with the real chord and the real description. OTHER renders only when it is non-empty, and it is empty today — 0 unmapped in the footer. Same enforcement shape as the missing description: the mistake is loud, not silent. spec §1.22

04A submap is a mode

The resize submap is a state machine, and it is the one place the overlay teaches one. Three obligations. The door: PUNAR+R · Enter resize mode carries a MODE tag in both surfaces — derived from the dispatcher being submap, not from a hand annotation — so it never reads as one more toggle. The room: the submap's own binds render in a bounded block with the mode named at its head and no modifier cap on any key, because those keys mean nothing outside it; the block's border is what says "only in here". The block prints the repeat flag the JSON already carries (HJKL · repeats while held) rather than a comment claiming it. The exit: both exits, always shown, never abbreviated to one. spec §13.3 · design language §7

05The mode chip

While a submap is active the bar prints the instrument chip D-007 already specified — RESIZE · HJKL · ESC: state, verbs, exit — in the centre zone D-016 reserved for modality and nothing else. The overlay and the chip are the same fact at two commitments: the chip is a persistent statement that you are in a mode, the block is the full key list you get by asking. A mode is never silent and never announced twice in the same place. D-007 Sect II·03 · D-016 Sect I·02 · spec §12.3

06Nothing org-specific

No section, no row and no footer in either surface knows whether the machine is enrolled. There is no "organization shortcuts" group, no policy-restricted chord greyed out with a citation, no managed annotation of any kind: the keyboard grammar is the operating system's, identical on a personal laptop and a fleet device, exactly as D-007's desktop is. If enrolment ever removes a binding it will remove it from the compositor's table, and the reference will stop printing it — annotation, never restructuring. design language §8 · spec §3.2 · §11

Sect IV · Chord typography register

A chord is typeset, not spelled — the modifier is the constant and the key is the variable, and the type must say which is which before the words are read.

01The cap

Geist Mono 500, 10 px, uppercase, +0.10em tracking, tabular-nums, 1 px border, 6 px radius, 3 px / 7 px padding — the tag idiom from the design language, at tag size. Tracking is 0.10em rather than the 0.12–0.14em of meta rows because a cap is a unit, not a label: it must hold together as one object. Caps sit on a 3 px gutter inside a chord and a 10 px gutter from the label. Terminal key caps carry a min-width of 22 px so a one-character key and a five-character key make the same silhouette down a column. design language §1 · §3

02Modifier vs key

Two weights of the same object. A modifier cap is ink-3 #666 on a #E6E4DE hairline with no fill — Punar — it recedes, because on a page of PUNAR chords it carries no information. A terminal key cap is ink #000 on an input-weight #8C8880 border with a #F4F2EC fill — Q — it is the thing that varies and the thing you are looking for. The eye lands on the key and the modifier stays legible without competing. design language §1 · §9.3

03Two modifiers

Modifiers chain outward-in, in the canonical order, joined by a 9 px ink-3 plus with 3 px either side: Punar+Shift+H. Both modifiers recede identically, so PUNAR+SHIFT+H and PUNAR+H differ by one inserted grey object and the same black key sits at the end of both — the reader compares the ends of the rows, which is where the meaning is. The plus is deliberately the keyboard vernacular and not a middle dot; the middle dot is the field note's separator for facts of equal weight, and these are not. design language §1 · §5

04The held modifier is silent

In the hold overlay every row shares the modmask by construction, so the modifier is stated once in the header — HOLDING PUNAR — and each row prints its key alone. Twenty-two rows of "PUNAR" would be twenty-two repetitions of the one fact the user's own hand is currently asserting. On panel the cap inverts: #F2F3F5 text on a #26282E hairline, no fill. In the help surface, where the modmask varies row to row, every chord prints in full. Same data, different context, different rendering — and the rule for which is mechanical, not editorial. design language §6 · spec §12.3

05A bare submap key

A key inside a mode must not read as a chord. It gets the cap silhouette but a filled ground and no companion — H — and it never appears outside the bounded mode block. Filled where a global cap is hollow, alone where a global chord has a modifier, enclosed where global rows are open: three signals that this key is only true inside this room. It would be cheaper to print "H" as plain text, and it would be wrong: bare text reads as prose, and this is still something you press. design language §1 · §7

06Monochrome, on purpose

Neither surface contains a single status colour. A keyboard reference has no status to report — nothing here is compliant, pending, expiring or denied — and the design language is explicit that a screen with nothing to report contains no colour. Consequences are exact: no green "available", no red "destructive" on PUNAR+Q or PUNAR+SHIFT+E (the compositor does not tell us which dispatchers are destructive, and inventing that judgement in a reference is the drift this plate exists to prevent), no colour-coded sections. The only ink that is not ink is the focus ring, and it is ink too: 2 px, offset 2 px, no colour dependence. design language §2 · §9.4 · spec §52

07Futures do not appear

keyboard-grammar.md's future table — clipboard history, media and brightness keys, lock/DPMS, per-workspace presets — produces no rows in either surface, dashed or otherwise. §7 says a dashed stroke marks a mechanism outside the current production claim, and in a diagram that is honesty; in a list of keys to press it is noise, because every row of this surface is an instruction and a dashed instruction is one the user will follow and be failed by. The roadmap has a home and it is the grammar document. The dashed strokes on this plate mark the surfaces themselves, which is the correct scope: the mechanism, not the content. design language §7 · spec §1.22

Sect V · Implementation notes

Design mockup — the help surface is a chord and an IpcHandler away, and the hold overlay is honestly blocked on a compositor question nobody has answered yet.

01Shortcuts.qml · IPC

New shell/punar-shell/Shortcuts/Shortcuts.qml, instantiated in shell.qml beside CommandCenter and Overview, with IpcHandler { target: "shortcuts" } and functions toggle() / open() / close() / state() — the exact contract shape the command center, overview and AI panel already use, and the same one the M2 CI exercise drives. Two layer surfaces inside it: the help PanelWindow (keyboard focus exclusive while open) and the hold overlay (keyboardFocus: none, empty input mask). One new variable in hyprland.conf: $shortcuts = qs -p /usr/share/punar/shell ipc call shortcuts toggle. shell/punar-shell/README.md · ipc.md

02The help bind

One line in punar-binds.conf: bindd = $mod, slash, Shortcut help, exec, $shortcuts — which, satisfyingly, means the help surface's own chord arrives in the help surface through the same transform as everything else, with no special case. No bind exists today. The mechanism, though, is proven three times over by shipped surfaces, which is why the help surface is drawn solid in the frame: §7's stroke claims the mechanism, not the merge. spec §12.3

03PUNAR-hold · the honest problem

Hyprland emits no "modifier held" event. There is no dispatcher, no socket2 event and no Quickshell property that says PUNAR is currently down, so the 400 ms hold must be assembled from press and release binds on the bare SUPER_L keysym — and every candidate has an open question on 0.56.2. (a) Release: bindr on PUNAR, SUPER_L is the established tap-to-launch idiom, so a release signal is very likely available — to verify that it fires after a chord as well as after a bare tap, since the overlay must hide either way. (b) Long press: recent Hyprland carries an o (longPress) bind flag; if it fires for a modifier-only bind, and if its delay is configurable, it is the design — to verify the flag exists in 0.56.2, applies to modifier keysyms, and exposes a delay. (c) Non-consuming press + shell timer: bindin on SUPER_L to arm a 400 ms timer in the shell, paired with (a) to disarm — to verify that a non-consuming bind on the modifier itself does not disturb the fifty-eight chords built on it, which is the risk that would make this unshippable. Nothing above is asserted as working; the frame draws the overlay dashed for exactly this reason. spec §1.22 · design language §7

04Failure modes and the fallback

A missed release — VT switch, session lock, a window grabbing the keyboard mid-hold — would strand the overlay on screen forever, so it carries a 10 s self-cancel regardless of what the compositor says, and it hides on any Hyprland focus-change event. If none of (a)–(c) verifies, the decision is already made: ship the help surface alone. PUNAR + / satisfies the second half of §12.3 with mechanisms that exist today, and half of a discoverability requirement met honestly beats a hold overlay that works on three machines out of four. The overlay is then a compositor task, not a shell task, and it is written down as one. spec §12.3 · §1.22

05Parse and cache

hyprctl binds -j runs once per session, lazily on the first open of either surface, through a Quickshell Process with a JSON parse inside a try — a malformed or empty result renders the calm empty state and never an exception. The parsed rows and the built sections are cached in memory; the surfaces re-render from the cache, never from a new query. Invalidation has exactly one trigger: a config reload. The shell listens on the socket2 stream it already consumes for configreloaded and drops the cache when it arrives (to verify — that 0.56.2 emits that event name on socket2; if it does not, the fallback is to invalidate on shell restart and on an explicit ipc call shortcuts reload, which is honest but manual). There is no poll, no timer and no file watch: at rest the whole feature costs one cached array and nothing else. While the overlay is held, per-frame work is zero — it is a static item with no animation, no countdown and no binding that re-evaluates. spec §6.3 · §11.8

06Counts today

punar-binds.conf at this plate's date: 64 described binds — 58 global plus 6 inside the resize submap — folding to 48 rows, of which 22 sit on PUNAR alone, 15 on PUNAR+SHIFT, 4 on PUNAR+CTRL, 1 on no modifier (Print), and 6 inside the mode. Zero undescribed, zero unmapped. Every number in the frame is computed from the same table the rows are, so this paragraph and the surface cannot disagree — and if they do, this paragraph is the one that is stale. os/modules/desktop/hypr/punar-binds.conf

07Milestone

keyboard-grammar.md books this as M2+ and it slipped; M9 and M10 are in flight. The plate asks for it in the milestone that picks up the remaining §12.1 keyboard flows — M11, alongside the battery/network/audio slots D-016 parked there — with the help surface as the shipping commitment and the hold overlay conditional on Sect V·03 verifying first. Acceptance is two lines: rename any binding's description in the config, reload, and see the new label in the surface without touching QML; delete a description, reload, and see the row disappear. spec §76 · §12.3
