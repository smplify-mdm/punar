Sect I · Engine register

Upstream-current Chromium plus a small, auditable integration layer — the fork we refuse to build is the claim.

01No fork

Punar does not build a browser engine and does not deep-fork Chromium. The integration layer is small enough to audit and rebase; the engine stays current. spec §30.1

02Security cadence

Browser security updates ship as critical OS security updates, independently of slower Punar feature releases. The engine never waits on us. spec §30.2

03Untouched model

Sandbox, site isolation, process boundaries, certificate validation, and extension security are upstream's — the integration layer may not weaken any of them, and no surface may claim otherwise. The install card's storage note is this rule as copy. spec §62

04Platform floor

PWA support, WebGPU, WebRTC, passkeys, extensions — inherited from upstream by staying upstream, never reimplemented. spec §30.1

Sect II · Citizen register

Installation is a contract the card states in full: what the app gets, and where its state lives.

01Install card

Raised from the command center, wearing the approval-card grammar: mono masthead, rule, one plain sentence, grants as chips. Install is a consequential affirmative — the one ok-green fill on the surface; Cancel stays ghost. spec §31 · §12.2

02Storage choice

Shared profile or separate context, chosen at install as two honest rows. The card says what separation is — cookies, storage, sign-ins — and refuses to call it a security boundary. spec §31 · §62

03Window identity

The titlebar is the masthead grammar — LINEAR · ATLAS with a context tag. No URL bar; identity is pinned to the installed origin and printed in the corner instead. It tiles, tabs, and answers Super-keys like any native window. spec §13 · §31

04Notifications

The toast carries the app's masthead name and its context, through the same notification surface native apps use — a citizen's channel, not a browser popup. spec §31

Sect III · Context register

Browser state follows the project — and enrollment adds a row, never a different screen.

01Isolation meta

Every context row states what it isolates: cookies · tabs · storage · identity. Silence is not isolation — the row is the coverage statement. spec §32

02Project forward

Switching to workspace Atlas brings the Atlas context forward automatically; the picker names the cause. Manual switching stays one keystroke away. spec §32 · §14

03Personal default

Unenrolled, the picker holds PERSONAL and the user's own project contexts — calm paper, no upsell, no empty org slot. spec §3.2 · design language §8

04Enterprise additive

Enrollment annotates: the ACME WORK row appears with certificate roots and network policy in its meta, a MANAGED pill, and a dashed SIMULATED tag while cert deployment is mocked. Existing rows do not move. spec §32 · §62 · §1.22

Sect IV · Implementation notes

Design mockup — the browser lands in Milestone 1; contexts and enterprise annotation follow the daemons.

01M1 · Browser

Package upstream Chromium with the Punar integration layer; install flow writes the launcher entry and window identity so punar-shell treats the app as native. Demo Step 13 is the acceptance test. spec §30 · §76

02M2 · Windows

App windows join tiling, tabbing, workspace assignment, and layout presets — no special cases in the window grammar. spec §13 · §31

03M3–M4 · Contexts

Context switching rides workspace state via punar-workspace; context definitions become declarative desired state with the rest of the machine. spec §14 · §38

04M5 · Enterprise

Mock Smplify enrollment adds the managed context row, extension and allowed-app policy, and certificate roots — dashed SIMULATED until the control plane is real. spec §62 · §77
