Sect I · Panel register

One question, answered completely: who, where, and by what route.

01Status band

Relay and DNS protection as chips with green presence dots — and the SIMULATED dashed tag whenever the claim isn't production yet (§1.22). In personal mode the relay is the user's own toggle; managed adds the MANAGED annotation, nothing more.

02Process list

The §64 view verbatim: every network-active process with its live connection count in tabular mono. AI sessions carry their attribution (AGT_123 · ATLAS) — the same identity chain as every other surface.

03Connection anatomy

Expanding a row shows the §37 tuple per destination: domain, reason category, route, project. Four columns, no payloads — the schema of what Punar knows is the proof of what it doesn't.

Sect II · Personal-first register

On a personal device, the most important row is the one that reads zero.

01punard's row

Personal mode: PUNARD · 0 CONNECTIONS · NOTHING TO REPORT HOME — the OS proves its own silence in the same list it uses to watch everything else. Managed mode: the row shows control.smplify.com · COMPLIANCE SYNC, because enrollment is visible, never ambient.

02Additive chrome

Switching modes changes annotations only — the enterprise route appears as a route value (ACME ROUTE) on existing rows, never as a redesign. DESIGN_LANGUAGE.md §8.

03Refusal as feature

The footer states the boundary: no content inspection. What the panel cannot show is a design commitment, not a missing feature (§37).

Sect III · Implementation notes

Design mockup — punar-netd builds this in Milestone 12; observability before relay.

01Data

Connection tuples from punar-netd's observation layer (process, destination, category, route, project, agent session — the §37 fields; matches schemas/network/). CLI parity: punarctl privacy connections.

02Relay honesty

The dual-hop plate ships dashed until the relay is real (Phase 2). A single-VPN implementation may never claim the dual-hop drawing — the §34 rule, enforced by stroke.
