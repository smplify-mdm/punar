Sect I · Registry register

Three classifications, three visual voices: managed is calm, observed is quiet, unknown is red.

01Agent rail

Every session from the registry (§19): name, project, session id, classification. Managed agents get the green presence dot; unknown gets the bad-red row — the only red in the panel unless something is wrong.

02Session line

The full attribution chain (§22/§47) as the detail masthead: AGT_123 · ALICE@ACME.COM · ATLAS-DEV-42 · STARTED 13:44 — same grammar as the approval overlay's identity line.

Sect II · Authority register — “may”

Authority is the promise: every row is a policy decision wearing its color.

01Decision grid

The §25 layout verbatim — filesystem, network, credentials, tools — with §20 decision words as tracked mono: ALLOWED green, DENIED red, REQUEST amber. Reading down the right edge tells the whole story.

02Live credential

Issued credentials show a live countdown (EXPIRES 41:32), amber in the final five minutes — short-lived by design (§29), and the panel makes the clock visible.

03Policy line

Authority cites its source: POLICY · ENG-AI-V3. One keystroke from the §40 explain view in System Control.

Sect III · Ledger register — “did”

The ledger answers a different question than authority — and the panel never lets you confuse them.

01May / did split

Authority and Ledger are stacked as separate ruled sections with their question in the section header — AUTHORITY · WHAT IT MAY ACCESS vs LEDGER · WHAT IT ACCESSED. This is §21's core distinction, made structural.

02Resource summaries

Level-3 aggregation only (§21.2): repositories, domains, credential classes, process classes with counts. No file paths, no prompts, no source code — the privacy rules are visible in what the UI *cannot* show.

03Security events

Level-4 events as red rows: DENIED · AWS_PROD CREDENTIAL · 14:02 · EVT_502. Denials are information, not noise.

04Privacy card

The §24.2 principle stated on the surface itself: the ledger stays on this device; admin queries are scoped, audited, and visible here. LAST ADMIN QUERY · NONE is a feature, not an absence.

Sect IV · Unknown-AI register

Detection is honest: “suspected,” never “certain” — visibility first, then policy.

01Unknown view

The §25 unknown-agent card: executable path, classification UNMANAGED · SUSPECTED AI, observed access (Atlas repository, api.foo.ai). Red voice throughout; no green anywhere on this screen.

02Actions

INSPECT, BLOCK NETWORK (a typed capability, approval-gated by policy), and REGISTER AS MANAGED — the constructive path out of the shadows (§23).

Design mockup — punar-agentd builds this in Milestones 7–8; the schemas already exist.

01Data

Rows come from the shipped contract layer: schemas/ai-agent/registry-record.json, ledger-summary.json, and the fixtures (agt_123, foo-agent) — this page renders those exact identifiers.
